Porting grimme-lab/xtb to WebAssembly

Feasibility study for in-browser GFN2-xTB IR spectra on ir.cheminfo.org · 28 August 2026
Evidence base: 15 research agents, 12 adversarially-verified claims, xtb at commit a45f05d (v6.7.1, 2026-08-09)

No-go today. The route exists in principle, but every available Fortran→wasm toolchain is currently unable to compile xtb — and we proved it by trying, on unmodified xtb dependency source.

There is exactly one possible route (patched LLVM Flang → wasm32-unknown-emscripten; f2c is F77-only, LFortran is alpha, gfortran has no wasm backend). Both prebuilt implementations of that route fail on the derived-type pattern that is xtb's universal error channel: one aborts, the other silently returns zeros.

The blocker is one specific, well-localized compiler defect — flang's semantics layer lays out derived types with a 64-bit long while the Emscripten runtime reads them as 32-bit. It is plausibly tractable, but fixing it is compiler engineering, not build configuration, and must be staffed and budgeted as such.

Everything else checks out: the compiler emits running wasm, -fdefault-real-8 behaves, node supplies argv/getenv/file-I/O/exit codes, and the exe_wrapper = node mechanism that runs xtb's test suite cross-compiled is measured-good. Your "all original tests pass" requirement is achievable operationally — and it eliminates every shortcut (trimmed builds, tblite-only, reimplementation all fail it outright).

1. Why xtb is a different problem from openbabel-wasm and surge-wasm

Your three existing ports — surge-wasm, openbabel-wasm, inchi-js — are C/C++ compiled with emcc, a path Emscripten supports natively. Emscripten has no Fortran front end. xtb is:

  • 322 .f90 + 51 .F90 files, ~176k lines, plus 5 mandatory Fortran subprojects (tblite v0.6.0, mctc-lib v0.5.1, dftd4 v4.2.0, multicharge v0.5.0, CPCM-X v1.1.0) — ~425k lines across 10 repos in total.
  • Uniformly modern Fortran: 1000+ class(...) declarations, 800+ type-bound procedures, select type, abstract interfaces, deferred-length allocatable strings, block, do concurrent, contiguous. Baseline is F2008; one file (tblite/src/tblite/integral/trafo.f90) needs F2018 — it uses ERROR STOP inside pure procedures 12 times, which F2008 forbids. Practical consequence: never build with -std=f2008.
  • Free of the genuinely hard features: zero coarrays, zero parameterized derived types, zero submodules in any src/ tree. That is what keeps this from being hopeless.

Everything downstream of "we have a .wasm" is already solved and templated in your repos — vendoring by pinned commit, patches under build/patches/, one build/build-wasm.sh, the gzipped+base64 wasm committed into a generated TS module, ESM-only publishing. The Fortran-to-wasm compiler is the only genuinely new problem.

One house-pattern setting must change. Your repos use -sSTACK_SIZE=1-2MiB. Fortran needs -sSTACK_SIZE=8MB or more — Emscripten's default is 64 KB and it fails silently; Fortran automatic arrays blow through it immediately.

Upstream LLVM still needs the patch — but it is tiny

Checked against the actual source of LLVM 23.1.0 (released 2026-08-25): flang/lib/Optimizer/CodeGen/Target.cpp dispatches over twelve architectures and falls through to TODO(..., "target not implemented"). So llvm#54832 (opened 2022) still reproduces today, and you will carry a patch.

The r-wasm/llvm-project wasm branch is 3 commits, 59 changed lines on LLVM 21.1.8: one adds a TargetWasm32 struct implementing only the COMPLEX argument/return ABI; two fix the array-descriptor model to use 32-bit index fields. Rebasing onto LLVM 22/23 is a mechanical edit (CodeGenSpecifics::get gained a targetABI parameter).

A trap worth knowing. miinso/flang-releases v21.1.8 is the only prebuilt flang with a macOS-arm64 host binary plus a wasm32 Fortran runtime — and it is silently broken. It compiles and links with zero diagnostics, then aborts inside the runtime on every test. Cause: flang derives its descriptor model from the host sizeof(long), so on arm64 macOS it emits i64 index fields that the wasm32 runtime reads as 32-bit. Always test a deferred-length string and an allocatable array before trusting any flang-wasm toolchain.

Two production users already do this

  • webR (Posit) ships BLAS and LAPACK 3.12.0 built for wasm32-unknown-emscripten with this exact toolchain, in production since webR 0.6.0 (2026-06-18, R 4.6.0). Four enabling fixes went upstream into LLVM permanently.
  • emscripten-forge ships flang_emscripten-wasm32 and uses it to build reference LAPACK, OpenBLAS with real Fortran, ARPACK and SciPy. But see §3.4: the spike found only versions 19.1.7 / 20.1.7, from a different patch series, and they fail more probes than r-wasm — so this prior art is real for F77-class Fortran and does not transfer to xtb.

Neither Pyodide (340 recipes) nor emscripten-forge (639 packages) contains any quantum-chemistry package. Nobody has packaged xtb, tblite or xtb-python for wasm — verified with exhaustive GitHub repo/code/issue/PR searches across the grimme-lab and tblite orgs, npm, and the web.

OpenMP: build serial first

Emscripten gained real OpenMP only in 6.0.3 (2026-07-13) via PR #27073, merged 2026-07-08 — and it does include the Fortran-callable entry points (kmp_ftn_cdecl.cpp). But the r-wasm image pins Emscripten 5.0.7, and so does this machine (verified: no omp.h). xtb makes OpenMP optional (-DWITH_OpenMP=OFF / -Dopenmp=false), its CI already runs green at OMP_NUM_THREADS=1, and threads in the browser drag in SharedArrayBuffer + COOP/COEP headers. Get a correct serial build first; treat threading as a separate performance project. (ir.cheminfo.org is self-hosted nginx/1.27.5, so it can set those headers when the time comes.)

3. The build spike — we tried it, and this is where it stops

Research can only tell you a route should work. This study went further and attempted the build, in Docker, on this machine. It stopped at milestone 1, and the reason is specific and reproducible.

3.1 What works

ghcr.io/r-wasm/flang-wasm:main (flang 21.1.8, default target already wasm32-unknown-emscripten) compiles Fortran to wasm that runs under node. Verified: hello-world, modules, formatted and list-directed I/O, a real host file round-trip via -sNODERAWFS, argv, getenv, and error stop 3 propagating to node exit code 3. -fdefault-real-8 -fdefault-double-8 verifiably flips kind(1.0) from 4 to 8.

Gotcha, recorded: -fdefault-real-8 alone promotes kind(1.0d0) to 16 (quad). Both flags are required together — exactly what xtb/cmake/CMakeLists.txt:57-58 already supplies for LLVMFlang.

That the exit code propagates matters beyond hello-world: it is the precise mechanism meson's exe_wrapper = 'node' and emcmake's CMAKE_CROSSCOMPILING_EMULATOR=node depend on. The cross-compiled-test-running machinery is measured-good — there is simply nothing to run through it yet.

A 10-probe suite was run through three compilers from the same source files — gfortran 15.2.0 native, flang-21 21.1.8 native (the identical upstream version, a perfect control), and flang-wasm → node:

p9/p10 are the worse finding. An abort is loud. Silently dropping derived-type default initialization — returning 0 where the source says 42, exit code 0 — is a wrong-answer bug in a quantum-chemistry code. It would surface as mysterious numerical disagreement, not as a crash.

3.3 Root cause — measured, not inferred

The compiler and the C toolchain disagree about pointer width on the same target:

FLANG-WASM, target wasm32-unknown-emscripten
  c_size_t = 8   c_intptr_t = 8   c_long = 8   storage_size(c_ptr)/8 = 8
EMCC C compiler, SAME wasm32 target
  sizeof(size_t) = 4   sizeof(intptr_t) = 4   sizeof(long) = 4   sizeof(void*) = 4

derived-type layout, flang-wasm vs native x86_64:  byte-identical (LP64)
  type with character(:),allocatable comp : 24 bytes  (both)
  type with real,allocatable(:)     comp : 48 bytes  (both)   <- LP64 descriptor

The shipped iso_c_binding.mod literally contains c_size_t=8_4. The r-wasm patch (3 commits) touches only the FIR→LLVM codegen path — Target.cpp, RTBuilder.h, DescriptorModel.h, TypeConverter.*. Nothing patches the semantics layer (compute-offsets.cpp, runtime-type-info.cpp), which lays out derived types and emits the __fortran_type_info tables using a host-compiled Descriptor where long is 8. The emcc-built libFortranRuntime.a then reads those tables as 32-bit → garbage DerivedType* → Initialize() no-ops → components never established → Assign reports "neither allocated nor allocatable".

This explains why webR works and xtb would not. The webR author describes the approach as "hard-coding the size of a long to what is needed for wasm32". That is sufficient for F77-class Fortran — LAPACK, BLAS, and the Fortran inside most R packages, none of which use derived types. It is insufficient for F2003+ OOP, which is exactly what xtb is built from. The existing production success does not transfer.

3.4 The second toolchain is worse

emscripten-forge's flang_emscripten-wasm32 was found only at 19.1.7 / 20.1.7 — not the 22.1.6 the desk research reported — and it is built from a different patch series (serge-sans-paille/llvm-project@feature/flang-wasm). It has the same c_size_t=8 defect and fails strictly more probes, including two that r-wasm passes (p3 “Null address”, p6 “Invalid descriptor”), plus a link failure on p2. Route closed.

Correction to the desk research: the claim that emscripten-forge ships flang 22.1.6 and builds LAPACK 3.12.1 / OpenBLAS 0.3.34 / SciPy 1.18.0 with it could not be reproduced — only 19.1.7 and 20.1.7 packages were found. Treat the “22.1.6” figure as unverified.

3.5 Reusable artifact

The 10-probe suite lives in experiments/fortran-wasm/probes/, with the mctc-lib reproduction in experiments/fortran-wasm/realcode/. It answers “is this candidate toolchain fit for xtb?” in minutes rather than weeks, and it should be the first thing run against any future flang-wasm build. That is the single most durable output of this study.

4. What an IR spectrum actually needs from xtb

Traced end to end in the source. xtb's IR path is a two-sided finite-difference Hessian over analytic GFN2 gradients: exactly 6N+1 single-point energy+gradient evaluations for N atoms (src/type/calculator.f90:151-186). IR intensities come for free from the SCF dipole already computed at each displaced point (dipgrad at calculator.f90:177, contracted at src/hessian.F90:521-533). There is no analytic Hessian and no analytic dipole derivative anywhere in xtb.

PropertyFinding
Dominant costSCF diagonalization — dsygst + dsyevd + dtrsm on an nao×nao matrix every SCC iteration (src/mctc/lapack/eigensolve.f90:230-244). Theory suggests O(N·nao³) ≈ O(N⁴); measured, it is N2.95 (r²=0.992 over 23 molecules, 3–98 atoms) — the Hessian is cheaper at realistic sizes than the theoretical exponent implies.
MemoryTrivial by browser standards: ~0.7 MB at 20 atoms, ~4 MB at 50, ~16 MB at 100. The wasm32 4 GiB ceiling is irrelevant here.
Runtime filesZero. GFN2, GFN1 and GFN-FF parameters are compiled into the binary (src/gfn_paramset.f90:59-82, src/gfnff/gfnff_param.f90:526-553); D4 reference data and all 40 GBSA/ALPB solvent sets are compile-time .fh includes (981 KB across 44 files). A GFN2 Hessian through the C API touches no filesystem.
C API43 bind(C) entry points. xtb_hessian (include/xtb.h:243-252, src/api/interface.f90:310-454) returns the Cartesian Hessian and dipole gradients — i.e. frequencies and IR intensities — bypassing the CLI and driver layers entirely.
Scratch filesNine files are written during a default --ohess run but none is read back, so Emscripten's MEMFS suffices.

The practical envelope for an in-browser, single-threaded xtb:

  • Interactive (< 10 s): up to roughly 25 atoms — benzene, hexane, caffeine, small drug fragments.
  • Tolerable with a progress bar (< 60 s): roughly 35–45 atoms — ibuprofen, estradiol.
  • Server territory (minutes): beyond ~60 atoms. Sildenafil is 4–9 minutes, cholesterol 5–12, β-carotene 15–34.

Your current server cap of MAX_ATOMS_XTB=60 is therefore roughly twice what the browser will serve comfortably. A hybrid — wasm below ~35 atoms, server above — covers the whole range behind one interface, and is the reason the recommendation keeps the server path alive rather than replacing it.

Two secondary findings from the same data: memory is a non-issue (peak RSS 38 MB at 96 atoms, nowhere near the wasm32 4 GiB ceiling), and the optimizer, not the Hessian, is the variance — floppy molecules cost far more cycles (sucrose 60, sildenafil 51, β-carotene 83, versus 4–7 for rigid ones), so pre-optimizing server-side or with a force field is a cheap win.

What your current service actually calls. cheminfo-py/xtbservice (behind ir.cheminfo.org's /v1/ir) does not use xtb's Hessian driver or CLI. It uses xtb-python's ASE calculator for single points and lets ASE's Infrared do the finite differences (xtbservice/ir.py:8-20), with ASE LBFGS for optimization. The 2026 successor, pipeline-workers/xtb-vibrational, says so explicitly. So the surface an in-browser xtb must reproduce is narrower than the CLI: energy + forces + dipole for a displaced geometry. Operational envelope today: MAX_ATOMS_XTB=60, TIMEOUT=100 s, OMP_NUM_THREADS=1.
A gotcha that will bite whoever writes the validation harness. --ohess does not build its Hessian at the geometry it writes out. Re-running --hess at the stored optimized coordinates moves the energy by ≤3.2e−11 Eh and frequencies by ≤0.06 cm⁻¹ — but IR intensities by up to 16% (cholesterol mode 204: 12.96 vs 11.17 km/mol). Validation fixtures must therefore store a Hessian generated by the exact protocol they will be compared against.

Related, and a property of the GFN2 surface rather than of any build: a single --ohess from a raw Open Babel geometry lands toluene and caffeine on methyl-rotor saddle points (ν₁ = −25.7 and −65.0 cm⁻¹). Don't use them as end-to-end fixtures.
A warning from your own code. pipeline-workers/xtb-vibrational/Dockerfile opens with FROM --platform=linux/amd64 and the comment "xtb's ARM64 build has numerical bugs that cause GFN2-xTB calculations to diverge." cheminfo has already been bitten by xtb diverging on a non-x86 target. A wasm32 port needs a numerical-agreement suite against the x86 reference from day one.

A reference data set now exists

Ten molecules (water → cholesterol) were run through obabel --gen3d → xtb --opt → xtb --ohess with GFN2, all confirmed true minima with zero imaginary modes, and stored as JSON fixtures with energies, frequencies, IR intensities, optimized geometries, timings and per-quantity tolerances: experiments/reference/ (61 files, 1.9 MB), plus a working two-tier harness (scripts/validate.py). 5. The "all tests pass" requirement

This constraint does more work than any other in the study. Full analysis in research/test-suite-requirement.md; the essentials:

5.1 The suite is small and portable

35 meson targets (34 OK + 1 expected-fail) / 40 ctest targets — 41 distinct targets in the union, neither command being a superset of the other. Inside the tester binary: 135 registered unit cases (119 without tblite), 1184 call check sites. Runtime ranges from 14 s (ifort+MKL, serial, optimized — the right base for extrapolating a single-threaded wasm run) to 80 s for a debug+coverage build. Runtime is not a risk.

5.2 The trap: a green summary proves nothing

test-drive skips are consumed inside the tester process (test/unit/main.f90:171), so a skipped case never increments the failure counter. Two CI jobs on the same commit — full build, and -Dtblite=disabled -Dcpcmx=disabled — print byte-identical summaries:

Ok: 34   Expected Fail: 1   Fail: 0   Skipped: 0   Timeout: 0

while actually executing 134 of 135 cases versus 104 of 119. Thirty cases disappear with no visible signal. A wasm build that fails to bring up tblite would print exactly what upstream prints. And tblite is likely forced off anyway: it needs libquadmath, an x86-only GCC runtime — which is already why tblite is disabled on aarch64 today, and wasm32 has no __float128.

Write the criterion as a skip allowlist, not a summary line. Require 104 PASSED / 15 SKIPPED / 0 FAILED with the 15 named explicitly, and require an identically-configured native build to produce identical per-suite counts. That last clause is what makes it a test of the port rather than of the flags. The rule to hold in review: skipping is defensible when xtb's own build system does the skipping; deleting never is.

5.3 Numerics are lower-risk than the usual port story

  • Every xtb assertion is absolute, never relative — verified, zero rel= hits across all 373 files. The tightest in the suite (test_gfnff.f90:154, 2.22e-13) still leaves ~2×10⁴ ULP of headroom.
  • Wasm is stricter than any native config xtb already passes: round-to-nearest only, no x87 extended precision, no scalar FMA contraction, no reduction reassociation. The only nondeterminism is NaN payload bits, which xtb never inspects.
  • Measured emscripten-musl vs macOS-arm64 libm over 200k points: sqrt bit-exact (and it is xtb's most-used math function, 691 sites), log/pow/exp/sin ≤1 ULP, erfc ≤6 ULP worst case.
  • The tolerances already survive gfortran 10–15, ifort, ifx, x86-64, aarch64, MinGW, and netlib/OpenBLAS/MKL substitution in xtb's own CI.

Estimate: 0–4 of 135 cases at real risk, concentrated in xtb/hessian, xtb/gfnff and ptb/polarizability. Probability the suite is green on the first successful compile: ~40%. After clearing latent uninitialized-variable UB natively and pinning netlib LAPACK: ~80%.

The realistic failure mode is not rounding — it is latent uninitialized-variable UB. Precedent: xtb#1109 broke 7 tests under GCC 14.1 and was fixed by removing an uninitialized variable, with no tolerance changed. Wasm's zeroed linear memory is a third initialization behaviour.

5.4 Measured: the wasm-shaped build is a cleaner gate than the default build

xtb 6.7.1 was built natively in Docker in four configurations and the full suite run (gfortran 13.3.0, OpenBLAS, OMP_NUM_THREADS=1; experiments/reference/testsuite/). The result is better than expected:

ConfigurationTargetsOKExpected failFailSkipWall

Two things fall out of this that matter for CI design:

  • The default build's single FAIL is not xtb's. It is multicharge / pbc → eeqbc-sigma-ice, an analytic-vs-numerical strain derivative off by 1.6e−8 on values of order 24 (relative 6e−10) against an upstream tolerance set too tightly for this compiler/arch. It is deterministic, it lives in a bundled dependency, and it is absent from the wasm-shaped build.
  • The 10 skips are a missing Python module (dftd4's tester.py exits 77 without pytest). Installing python3-pytest converts all ten to passes — and then exposes an order-dependent failure: an xtb CPCM-X test writes smd_h2o into the shared build directory and numsa's cds test then reads that stale file. Verified directly. Test-harness pollution, not a code defect — and numsa is not built in the wasm-shaped configuration either.

So configuration B is the better CI gate: fewer moving parts, no third-party noise, zero skips at target level, and it is the configuration the wasm port would use anyway.

The exact skip allowlist, measured

At subtest level, A runs 135 (134 passed, 1 skipped) and B runs 119 (104 passed, 15 skipped). The inventory shift is exact and explainable: PTB is built on tblite, so A's 17 real ptb subtests are replaced by a single guard — 135 − 17 + 1 = 119.

  • eeq / hbond — "Not implemented", a genuine upstream gap, skipped in both configurations
  • 11 × tblite/* and ptb / ptb_not_present — "xtb not compiled with tblite support"
  • dipro / J_ab,eff — "tblite libary not available."
  • cpx / solvation — "CPCM-X libary not available."

Each skip names its own reason, which makes the allowlist auditable rather than a bare count. None of the 15 touches the GFN2 IR path — GFN2 through xtb's own calculators is covered by xtb:unit / gfn2 and xtb:unit / hessian, both passing in B.

5.5 The numerics question is now answered: the spread is zero

Six variants across all ten reference molecules — identical rerun, 4 BLAS threads, an OpenMP build at 1 and at 4+4 threads, and true netlib reference LAPACK+BLAS forced via LD_LIBRARY_PATH: every delta exactly zero in energy, frequency and intensity. A further build at -O1 with FMA contraction disabled and a swapped LAPACK backend reproduced the fixtures exactly; the Cartesian Hessian was bit-identical for the eight smallest molecules and differed by 1e−10 (one ULP of the printed value) on the two largest.

Watch out for a false negative here. Ubuntu's liblapack.so.3 alternative points at OpenBLAS, so -Dlapack=netlib alone does not give you netlib. The genuine reference implementation had to be forced with LD_LIBRARY_PATH and confirmed with LD_DEBUG=libs. Any "we tested both backends" claim that skips this step tested one backend twice.

The noise is real but never reaches a printed digit: caffeine's gradient components differ at ~1e−16 Eh/a₀ between backends while the energy agrees to all 11 printed decimals. The SCF is a converged fixed point, and that is what absorbs the difference.

The risk is the geometry, not the arithmetic. Perturbing the input geometry and running the full pipeline:

5.6 Two tests can never be a reliable gate

xtb/symmetry (4 cases) rattles geometries with unseeded random_number (test_symmetry.f90:234-250), so upstream CI already tests a different geometry every run. xtb/random (3 cases) needs the wasm Fortran runtime to implement random_seed(size=/get=/put=) correctly. Pin these expectations before they become contractual.

Prior art that changes the fallback calculus

Nobody has ported Fortran xtb to wasm (verified negative). But @peterspackman/occjs @0.9.3 (2026-08-05) — OCC, a ~9000-line C++17 GFN2-xTB reimplementation developed against xtb/tblite references and agreeing "to single µHa on small molecules" — is already compiled to wasm with emcc/embind and published on npm. An agent installed it and ran it under Node 26: water E = −5.07025643 Ha; a numerical Hessian giving 1573.9 / 3573.6 / 3668.0 cm⁻¹ in 51 ms; benzene's full 36-mode Hessian in 1.04 s. It exposes no dipole derivatives, so IR intensities are the missing piece — band positions come free. It runs none of xtb's tests, so it cannot satisfy your requirement, but it is a strong comparison point and a plausible interim product. Also relevant: ExaPsi/IQCP (Rust→wasm) does HF/DFT with analytic Hessians, IR and Raman entirely client-side at iqcp.dev.

7. Licensing — two decisions to make before the first release

  • xtb is LGPL-3.0-or-later, but symmetry/symmetry_i.c (Patchkovskii's symmetry analyzer) is GPL-2.0-or-later, which would make a statically linked xtb.wasm a GPL-3.0 combined work. It is used only for the thermostatistics rotational symmetry number (src/thermo.f90:59 ← src/main/property.F90:1344), never for frequencies or intensities. Dropping it keeps the artifact pure LGPL — but it also drops the 4 xtb/symmetry tests, which collides with your requirement. Decide deliberately: pure-LGPL artifact, or literal test parity.
  • Because wasm has no shared-library mechanism, LGPL-3 §4(d)(1) is unavailable — you must satisfy §4(d)(0) by publishing the full build tree plus linkable objects so a user can relink a modified xtb. The clean precedent is ffmpeg.wasm: @ffmpeg/ffmpeg is MIT while @ffmpeg/core (the package holding the .wasm) is declared GPL. Note the asymmetry: serving a .wasm is conveying; a server-side API conveys nothing.
  • Dependencies split LGPL-3 (tblite, dftd4, CPCM-X) and Apache-2.0 (mctc-lib, multicharge, toml-f); LAPACK/OpenBLAS are BSD.

8. Recommendation

Do not start the port. Spend hours — not weeks — answering one question first, and keep the server-side path running regardless.

The sequencing changed because of §3. The expensive milestones (LAPACK to wasm, building xtb, running the suite) are all downstream of a compiler that does not currently work on xtb's Fortran. Doing them now would be building on sand.

  1. Step 1 — is the bug already fixed upstream? (hours, do this first.) Run the saved p1..p10 probe suite against any flang ≥ 22 targeting wasm32. If it passes, the blocker is gone and this becomes a straightforward path. This is by far the highest leverage per hour in the whole project.
  2. Step 2a — if it passes: native hygiene (2–3 days). Run xtb's suite natively with -finit-real=snan -finit-integer=-99999999 -finit-logical=true -ffpe-trap=invalid,zero,overflow and fix what it finds — this is where every historical cross-compiler failure lived. Then build xtb with flang natively; nobody ever has, and a native flang failure is far cheaper to debug than a wasm one.
  3. Step 2b — if it fails: decide whether to fund a compiler milestone. Extend r-wasm's patch series into flang's semantics layer (compute-offsets.cpp, runtime-type-info.cpp, TargetCharacteristics), rebuild LLVM+flang+MLIR on a native linux-amd64 host (many hours, tens of GB — not under Rosetta), and re-run p1..p10 plus the mctc-lib reproduction. This is a genuine project risk, not a formality: that patching the semantics layer is sufficient is a hypothesis, and there may be further host-long assumptions downstream. Budget it as compiler engineering with an uncertain tail, or find someone upstream to do it.
  4. Step 3 — in parallel, independent of the bug: build reference LAPACK/BLAS to wasm. This is F77-class Fortran, which the current toolchain already handles, so it can be de-risked today. Build netlib LAPACK 3.12.1 + reference BLAS with the same flang and smoke-test dgemm/dsyev under node. Doing it with the same flang is what makes the ABI self-consistent and avoids the f2c signature-mismatch trap (§10).
  5. Steps 4–6 — only after a working compiler: build xtb via CMake (not meson — only CMake has the LLVMFlang branch supplying -fdefault-real-8), run ctest through CMAKE_CROSSCOMPILING_EMULATOR=node with the skip allowlist from §5.2, then package down your existing house pattern with -sSTACK_SIZE=8MB and an extern "C" JSON-envelope shim over xtb_hessian. Estimating these now would be false precision.

What to do about ir.cheminfo.org in the meantime

  • Keep the server path. It is the only thing that satisfies your test requirement today, and §4's cost model says it must stay anyway for molecules above ~45 atoms. Architect the TypeScript client so a wasm backend can slot in behind the same interface later — that is the cheap insurance.
  • Evaluate @peterspackman/occjs now. It already runs GFN2-xTB in the browser (benzene's 36-mode Hessian in 1.04 s, measured) and gives you correct band positions immediately. Its gap is IR intensities — it exposes no dipole derivatives. Adding those to a 9k-line C++ codebase you can compile with the emcc toolchain you already master is a far smaller, far more predictable job than fixing LLVM Flang. If the goal is "IR spectra in the browser" rather than "xtb in the browser", this is the shortest credible path — but note it satisfies none of your test requirement, so it is a product decision, not a compliance one.

10. Risks, unknowns, and what was refuted

  • Resolved by the spike, and it is the headline: no wasm build of xtb was produced, because no available toolchain can compile xtb's dependency source at all (§3). flang has still never been shown to compile xtb natively either — that remains untested and is now step 2a.
  • The load-bearing hypothesis: that patching flang's semantics layer to use 4-byte pointers and a 32-bit CFI_index_t on wasm32 clears the blocker. The root cause is measured; that this fix is sufficient is not. There may be further host-long assumptions downstream. The entire project now rests on this.
  • The reference fixtures are aarch64-only, generated with gfortran 13.3.0 on Apple Silicon Docker. Your own pipeline-workers/xtb-vibrational pins --platform=linux/amd64 because "xtb's ARM64 build has numerical bugs" — yet this study measured zero spread on aarch64 across every backend, thread count and FP setting tried. Those two facts are in tension. Regenerate the fixtures on amd64 and diff them: it either confirms your ARM64 note or retires it, and it costs one Docker run.
  • Only error_type was measured against real xtb-family source. Whether all ~1000 class(...) sites are affected or only some is unknown — irrelevant to go/no-go (one blocked site on the universal error path is enough), but relevant to post-fix risk estimation. Next step once a fixed compiler exists: compile mctc-lib and toml-f standalone and run their suites under node before touching xtb.
  • Everything downstream of a working compiler is unmeasured: whether src/mctc/signal.c builds under emcc, whether NODERAWFS holds at test-suite scale, GFN2 numerical agreement wasm-vs-native, build wall-time, and final .wasm size. Do not estimate these from this study.
  • flang-rt's Fortran I/O layer is unvalidated on wasm. emscripten-forge's build disables all runtime tests; its entire validation is one PRINT *. Nothing exercises OPEN/READ/WRITE/INQUIRE or scratch files. flang-rt/lib/runtime/file.cpp:33-58 hard-codes /tmp/Fortran-Scratch-XXXXXX + mkstemp — fine under NODERAWFS, impossible under WASI.
  • WASI is ruled out mechanically, not on maturity: wasi-sdk 34's libc has no signal, tmpfile, mkstemp or system, and src/mctc/signal.c does not even compile for wasm32-wasip1 — while being on the critical path of every unit test via mctc_init.
  • LAPACK ABI is the classic killer, and it is avoidable. flang emits the f2c convention (trailing underscore, by-reference, hidden CHARACTER lengths as trailing i32, COMPLEX via sret) — but f2c/CLAPACK declares subroutines as int foo_() where flang expects void, and omits the trailing ftnlen arguments. Symptom: wasm-ld: warning: function signature mismatch then RuntimeError: unreachable at call time, with no linker flag to relax it. Compile reference LAPACK from Fortran with the same flang and the problem does not exist.
  • Refuted during verification: the claim that "no component requires Fortran 2018" — tblite v0.6.0 needs F2018 for ERROR STOP in pure procedures. Also corrected: findloc and impure elemental are F2008 features, so their absence proves nothing about F2018.
  • Acceptance scope is genuinely ambiguous and must be pinned. "All the tests of the original project" is not what upstream runs: meson filters --suite xtb, CTest's -R 'xtb/*' is a substring regex, and CI explicitly excludes tblite/gfn1-xtb. The literal reading — ninja test with no filter, 131 targets across six subprojects — has never been run by upstream on any platform. Do not let it become the contract by default.
